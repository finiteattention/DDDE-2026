## **TITLE**

**Making a complex domain legible to users: replacing a Word template with a digital tool for Data Protection Impact Assessment.**


## **DESCRIPTION**

How do you make risk assessment a process users don't describe as "hellish"?

The Norwegian Labour and Welfare Administration (Nav) handles a lot of information about citizens. Like any public body, Nav must comply with many different regulations about processing of personal information, GDPR being just one example. Of course, it's unreasonable to expect software development teams, facilities management, benefits offices etc, to each have the expertise required to understand and document compliance with many different laws, and to keep up with legislative changes. Previous work at Nav has developed a digital self-assessment tool to help colleagues work through Nav's "success criteria" for compliance with a range of different regulations. The tool models the legislative material in a highly structured way, with requirements descriptions and success criteria being owned and kept updated in the tool by subject specialist "requirements owners".

Where processing of citizens' data poses potential risk to their privacy rights, teams may also need to complete a Data Protection Impact Assessment (DPIA). DPIA involves identifying and estimating risks, then implementing measures to reduce the level of risk. Until recently, DPIA in Nav was documented, reviewed and signed off using a Microsoft Word template. Word as a format was challenging for users (many of whom are not familiar with DPIA or privacy legislation), for Nav's data privacy ombudsman who reviews DPIAs and returns them with feedback, and for risk owners in the organisation who need an up to date overview of their risk portfolio.

This talk will outline how Nav went from using Word for DPIA, to building integrated support for DPIA into the existing compliance tool. The talk will demo the tool itself (in production since September 2025) and touch on:

* What happens to the user experience, and domain knowledge, when a documentation tool (Word) is too simple for the domain being documented.

* Using domain mapping and user feedback to decide how to integrate new functionality into an existing tool.

* Practical design considerations when allowing users to complete their regular compliance documentation and their DPIA side by side. 

* Designing for users to create and re-use their own content while retaining an overview of what is used where.

* Designing to make it as hard as possible to produce a "bad" DPIA.

* Integrating functionality for three distinct user groups, each with different requirements, into the same tool.

* Designing with data in mind from the beginning. 

* Harnessing user pains to prioritise feature development

* Using cognitive load as a lens to guide design choices.
